👋 New to auth? Here's the 3-minute map: 1️⃣ Users sign up with a hashed password (never plain text). 2️⃣ On login the server hands them a JWT (a signed "ID badge"). 3️⃣ Every later request sends that badge in the Authorization header so the server knows who they are. Then we ship it all to the internet.

2. Authentication vs Authorization

🚩 Why it matters: two words, two jobs. Mixing them up causes bugs.
AUTHENTICATION  = WHO are you?        (login / register)   → proves identity
AUTHORIZATION   = WHAT may you do?     (permissions)        → allows actions

Check-in at a hotel = authentication (show ID). Getting a key card only to your room = authorization.

🎯 Section 2 quiz

"Show your ID to prove who you are" is…

Authentication

"You may only edit YOUR OWN notes" is…

Authorization

"Log in with your email & password" is…

Authentication

3. Passwords done right — hashing with bcrypt

🚩 Why it matters: storing plain-text passwords is a disaster. Hashing scrambles them one-way.
🧪 Try it: in the 🔐 auth panel below, click Register — watch how your password is NEVER shown/stored as-is, only a "hash".
// NEVER store the raw password:
user.password = req.body.password;        // ❌ bad: relation — if DB leaks, passwords leak

// DO store a HASH (one-way, can't be unscrambled):
const bcrypt = require("bcrypt");
const saltRounds = 10;                     // makes it slower = harder to crack
const hash = await bcrypt.hash(req.body.password, saltRounds);
user.password = hash;                      // ✅ store only the hash

// To CHECK a login: bcrypt re-hashes and compares in one safe step
const ok = await bcrypt.compare(typedPassword, savedHash);
if (!ok) return res.status(401).json({ error: "Wrong password" });

🎯 Section 3 quiz

Why NOT store plain-text passwords?

If the database leaks, passwords are exposed — hashing makes them useless

Can you turn a hash back into the password?

No — it's one-way

How do you CHECK a password at login?

bcrypt.compare(typed, savedHash)

4. JWT — the three parts

🚩 Why it matters: a JWT is the "ID badge" the server issues so it can trust the user WITHOUT re-checking the password every request.
jwt.sign({ userId, name }, SECRET, { expiresIn: "7d" })
// → a long string:  header.payload.signature

 JWT = HEADER . PAYLOAD . SIGNATURE
        (type)    (data)   (tamper-proof seal)
🧪 See it live: after Logging in the auth panel, the token shows as 3 coloured chips: header · payload · signature.
  • Header — says "I'm a JWT".
  • Payload — the safe claims like userId (NOT the password).
  • Signature — a cryptographic seal from the server's secret; if anyone edits the token, the seal breaks.

🎯 Section 4 quiz

How many parts does a JWT have?

3 — header, payload, signature

Does the payload contain the password?

No — only safe claims like userId

What does the signature do?

Proves the token wasn't tampered with

5. Register a user (backend)

🚩 Why it matters: signup must validate input, hash the password, and avoid duplicate emails.
app.post("/api/auth/register", async (req, res) => {
  const { email, password } = req.body;

  const exists = await User.findOne({ email });
  if (exists) return res.status(400).json({ error: "Email already used" });
  if (!password || password.length < 6)
    return res.status(400).json({ error: "Password must be at least 6 chars" });

  const hash = await bcrypt.hash(password, 10);       // hash, not plain
  const user = await User.create({ email, password: hash });
  res.status(201).json({ message: "User created" });  // NEVER return the hash
});

🎯 Section 5 quiz

What must registration do to the password?

Hash it with bcrypt before saving

What if the email already exists?

Return 400 "Email already used"

Should the response include the saved hash?

No — never return the password/hash

6. Login & issuing a token

🚩 Why it matters: login checks the password, then issues a JWT the client uses for later requests.
app.post("/api/auth/login", async (req, res) => {
  const { email, password } = req.body;
  const user = await User.findOne({ email });
  if (!user) return res.status(401).json({ error: "Bad credentials" });

  const ok = await bcrypt.compare(password, user.password);
  if (!ok) return res.status(401).json({ error: "Bad credentials" });

  const token = jwt.sign({ userId: user._id, email: user.email }, SECRET, { expiresIn: "7d" });
  res.json({ token, user: { id: user._id, email: user.email } });
});

🎯 Section 6 quiz

What does the server hand back on successful login?

A JWT token (plus safe user info)

What status for wrong email/password?

401

What goes in the JWT payload?

user.id and email — never the password

7. Protecting routes with middleware

🚩 Why it matters: middleware checks the token BEFORE the route runs, so private data stays private.
function auth(req, res, next) {
  const header = req.headers.authorization;              // "Bearer <token>"
  if (!header || !header.startsWith("Bearer "))
    return res.status(401).json({ error: "No token" });
  const token = header.split(" ")[1];
  try {
    req.user = jwt.verify(token, SECRET);                // seal OK → user known
    next();                                               // 🔓 carry on to the route
  } catch {
    res.status(401).json({ error: "Invalid or expired token" });
  }
}
app.get("/api/me", auth, async (req, res) => {
  res.json({ user: req.user });                          // only if token valid
});

🎯 Section 7 quiz

What does the middleware do before the route runs?

Verifies the JWT in the Authorization header

What if no/invalid token?

Return 401 without running the route

How is a private route marked?

Pass `auth` as middleware before the handler

8. Using the token in React

🚩 Why it matters: the frontend stores the token (localStorage) and sends it in the request header.
async function login(email, password) {
  const res = await fetch("/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });
  const data = await res.json();
  localStorage.setItem("token", data.token);        // remember the badge
  setUser(data.user);
}
async function loadMe() {
  const token = localStorage.getItem("token");
  const res = await fetch("/api/me", {
    headers: { "Authorization": "Bearer " + token }, // send the badge
  });
  if (res.status === 401) { setUser(null); return; } // expired → log out
  setUser(await res.json());
}
🧠 memory aid: login → localStorage.setItem("token", …) → every protected call sends Authorization: Bearer token.

Log the user out (token expired)

10. Deployment — what it actually means

🚩 Why it matters: your app on localhost only works on YOUR computer. Deployment puts it on the internet for everyone.
🌍 Before: url is localhost:3000 — only you. After: url is myapp.onrender.com — anyone with the link.
Deploying a MERN app = hosting 3 things:
  1. BACKEND (Express)   → Render / Railway / Fly.io
  2. FRONTEND (React)    → Vercel / Netlify
  3. DATABASE (MongoDB)  → MongoDB Atlas (cloud)

Each hosting company gives your piece a public URL, and they talk to each other over the internet.

🎯 Section 10 quiz

What 3 pieces do you host for MERN?

Backend (Engine), Frontend (React), Database (MongoDB)

Where does the database live in production?

MongoDB Atlas (cloud)

11. Hosting the backend (Render) + env vars + Atlas

🚩 Why it matters: the server needs a public home, plus secrets (DB URL, JWT secret) set as env variables — never hard-coded.
// .env (DO NOT commit this file!)
PORT=3000
MONGODB_URI=mongodb+srv://user:pw@cluster.mongodb.net/
JWT_SECRET=make-up-a-long-secret-string

// server.js reads them
const PORT = process.env.PORT || 3000;
mongoose.connect(process.env.MONGODB_URI);
const SECRET = process.env.JWT_SECRET;   // used by jwt.sign / jwt.verify

Steps to host the backend on Render: 1️⃣ push your code to GitHub · 2️⃣ New → Web Service · 3️⃣ pick the repo · 4️⃣ Set start command `node server/server.js` · 5️⃣ add the .env secrets in Render's "Environment" tab · 6️⃣ Deploy → get a public URL.

🧠 never commit secrets: add .env to .gitignore. Use env vars in the host (Render/Vercel) instead.

🎯 Section 11 quiz

Where do secrets live in production?

Environment variables (Render's env tab / .env, not hard-coded)

What two secrets do you almost always need?

MONGODB_URI and JWT_SECRET

Should .env be committed to git?

No — add it to .gitignore

12. Hosting the frontend (Vercel / Netlify)

🚩 Why it matters: the React screen needs a public URL, and its fetch calls must point at the hosted backend (plus CORS).
// BAD: hard-coded localhost (won't work after deploy)
fetch("http://localhost:3000/api/notes");

// GOOD: use an env var at build time
fetch(import.meta.env.VITE_API_URL + "/api/notes");
// Vite .env →  VITE_API_URL=https://my-backend.onrender.com

Steps: 1️⃣ build the app (`npm run build`) · 2️⃣ connect the repo to Vercel/Netlify · 3️⃣ add VITE_API_URL as an env var · 4️⃣ deploy → get a public URL. Then update the backend's CORS to allow your new frontend URL.

🎯 Section 12 quiz

What must the frontend's fetch URLs use in production?

The hosted backend URL via an env var (VITE_API_URL)

After moving the frontend to a real domain, what must you update on the backend?

CORS to allow the new frontend origin

13. Testing basics

🚩 Why it matters: a test is just code that checks your code. It catches regressions before users do.
// A test = describe what should happen + assert it
// Example (Vitest / Jest style):
function hashPassword(pw){ return pw.split("").reverse().join(""); } // fake demo
test("hashPassword scrambles", () => {
  expect(hashPassword("abc")).toBe("cba");
  expect(hashPassword("abc")).not.toBe("abc");
});

Mental model: write a tiny function that calls your real function and asserts the result. If the function breaks later, the test turns red and tells you.

🎯 Section 13 quiz

What does a test do?

Asserts your code behaves as expected, catching regressions

When a test "goes red", what does it mean?

Something broke — fix it before shipping

14. Routing libraries (React Router)

🚩 Why it matters: real apps have multiple pages (Home, Login, Profile). React Router maps URLs to components.
// App.jsx with React Router (react-router-dom)
import { BrowserRouter, Routes, Route, Navigate } from "react-router-dom";
import { useAuth } from "./AuthContext";

function App() {
  const { user } = useAuth();
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/login" element={<Login />} />
        <Route path="/profile" element={user ? <Profile /> : <Navigate to="/login" />} />
      </Routes>
    </BrowserRouter>
  );
}

🎯 Section 14 quiz

What does React Router do?

Maps URL paths to components (pages)

How do you protect a /profile page in React?

Redirect to /login if not authenticated (Navigate)

15. Common production pitfalls

🚩 Why it matters: these are the 5 mistakes that break deployed apps.
1. Storing plain-text passwords               ❌  →  always bcrypt.hash
2. Hard-coding the JWT secret / DB URL        ❌  →  use env vars (.env / host env tab)
3. Committing .env to GitHub                  ❌  →  add to .gitignore
4. Forgetting CORS on the deployed backend    ❌  →  allow your real frontend URL
5. Frontend still calls localhost after deploy ❌  →  use VITE_API_URL env var
6. Putting the password IN the JWT payload    ❌  →  only userId/email, never secrets

🎯 Section 15 quiz

Deployed frontend can't reach the API? First check?

CORS on the backend + the API URL env var

Your .env got pushed to GitHub? What's the lesson?

Add .env to .gitignore; rotate the leaked secrets

Should the JWT payload contain the password?

Never

Return the headers object for a fetch call, adding Authorization: "Bearer " + token, keeping any existing headers.
